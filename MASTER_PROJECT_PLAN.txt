============================================================ 1. PROJECT
GOALS AND NON-GOALS
============================================================

MAIN GOALS - Convert English dialogue in a video into natural Hindi. -
Preserve the source speaker’s vocal identity as closely as the tested
models allow. - Preserve emotion and delivery where possible: calm,
excited, angry, sad, whispering, emphasis, pauses, and rhythm. -
Maintain consistent voices for the same speakers across a clip. - Keep
Hindi dialogue timing reasonably aligned with the original scene. -
Preserve original background music and sound effects when they can be
separated reliably. - Export a playable MP4 and optional Hindi
subtitles. - Provide both a Windows desktop interface and a local web
interface. - Keep all video/audio inference and processing on the user’s
own computer. - Benchmark models on identical clips before choosing
defaults.

IMPORTANT LIMITATIONS - Do not promise an exact replica of a real voice,
perfect emotion preservation, or perfect lip synchronization. - English
and Hindi sentences have different lengths and grammatical structures.
Timing may require translation adaptation, speech-rate adjustment,
pauses, or limited silence changes. - Voice similarity, Hindi
pronunciation, translation quality, and expressive delivery can
conflict. Expose quality settings instead of claiming one model is best
at everything. - Lip-sync tools may modify faces and can have quality,
licensing, and compatibility limitations. Treat lip sync as optional and
separate from the first working dub. - Source separation can introduce
artifacts. Include a mode that keeps the original audio when separation
quality is poor. - Do not train a large model from scratch for the
initial project. Start with compatible pretrained models and evaluate
them.

============================================================ 3. MODEL
SELECTION AND BENCHMARK POLICY
============================================================

Model names below are candidates, not pre-approved guarantees. Before
integration, verify current repositories, checkpoints, licenses,
supported language pairs, installation requirements, and local inference
support.

A. SPEECH RECOGNITION Candidate: faster-whisper using a small or medium
model according to measured VRAM. Benchmark: - Word error rate if a
corrected reference transcript is available. - Names and punctuation
accuracy. - Timestamp alignment. - Runtime and peak VRAM/RAM. -
Robustness to music and noisy dialogue.

B. ENGLISH-TO-HINDI TRANSLATION Candidate: IndicTrans2 and at least one
suitable local multilingual alternative. Benchmark: - Meaning
preservation. - Natural spoken Hindi, not merely literal translation. -
Correct pronouns, gender, tense, names, idioms, and context. -
Consistency across adjacent lines. - Human review of the same test
examples. - Runtime and memory. Do not translate each tiny segment
without context if that harms meaning. Pass neighboring lines and
speaker context when supported, while maintaining segment boundaries.

C. HINDI SPEECH GENERATION AND VOICE REFERENCE Candidates to
investigate: XTTS-v2, OpenVoice with a compatible Hindi base TTS if
technically valid, and other currently maintained local Hindi-capable
TTS/voice-cloning models discovered during research. Before choosing: -
Confirm Hindi output works in the actual checkpoint, not just in a
marketing description. - Confirm cross-language voice reference is
supported for English source voice to Hindi output. - Confirm the model
runs within 6 GB VRAM or has a documented CPU/offload fallback. - Check
license and use restrictions. - Test Hindi pronunciation and voice
similarity using authorized reference audio. - Check whether
emotion/prosody controls are genuinely supported. - Record dependency
conflicts and setup complexity. Do not claim that voice identity or
emotion is preserved if the model only generates a generic voice.

D. EXPRESSIVE SPEECH TRANSLATION RESEARCH SeamlessExpressive may be
studied as a reference for expressive speech translation, but do not
assume it supports English-to-Hindi output. Confirm the exact supported
language pair before any integration. OpenVoice V2 has published
native-language limitations; do not assume Hindi output merely because
cross-lingual voice cloning is advertised. A compatible Hindi base TTS
must be demonstrated in a test. Do not make a research model a required
runtime dependency unless it passes the project tests.

E. SOURCE SEPARATION Candidate: Demucs or a maintained compatible
alternative. Treat as optional because separation can use substantial
VRAM and can introduce artifacts. Compare: - Dialogue intelligibility
after separation. - Music/effect artifacts. - GPU memory and runtime.
Provide a no-separation fallback.

F. OPTIONAL LIP SYNCHRONIZATION Investigate Wav2Lip or an appropriate
maintained alternative only after the audio dubbing pipeline is
reliable. Check license and usage conditions carefully. Keep lip
synchronization off by default until the user enables it. Do not make
face modification a prerequisite for exporting a dubbed video.

BENCHMARK SET Create 5–10 short, user-authorized clips covering: - Clear
single-speaker neutral dialogue. - Fast speech. - Emotional speech. - A
clip with background music. - A clip with names or idioms. - A
multi-speaker clip after single-speaker tests pass. Start with one 15–30
second single-speaker clip to prove the pipeline.

For every run, record: - Test clip ID and duration (avoid storing
private original media in reports). - Model name, exact
revision/checkpoint, configuration, and license reference. - Operating
system, Python version, CUDA/PyTorch versions, GPU name. - Processing
time per stage and total processing time. - Peak VRAM and RAM if
measurable. - ASR reference error rate where reference text exists. -
Translation review score. - Hindi intelligibility and pronunciation
score. - Voice similarity score and method used. - Emotion/prosody
review score. - Timing mismatch and final output validation. - Known
failures and human notes.

Suggested initial weighted quality score: - Translation accuracy: 25% -
Naturalness and Hindi intelligibility: 20% - Voice identity similarity:
20% - Emotion and prosody: 15% - Timing fit: 10% - Runtime and memory
efficiency: 10%

These are project-defined weights, not published results. Keep the
individual scores visible. Do not let a high total score hide a severe
failure in Hindi output or voice identity. Human listening is mandatory
for subjective qualities; automated speaker embeddings are only
supporting evidence.

============================================================ 4.
ENGINEERING REQUIREMENTS FOR ALL PHASES
============================================================

ERROR HANDLING - Use structured exceptions and actionable messages. -
Include the failed pipeline stage, a short explanation, and a safe next
step. - Keep detailed logs local and do not log transcript/audio content
by default. - Never swallow exceptions silently. - Retry only transient
failures; do not repeatedly retry invalid inputs or out-of-memory
errors.

PERFORMANCE - Keep one GPU-heavy stage active at a time by default. -
Load models lazily and release them after use when practical. - Expose
device selection only when the option has been tested. - Monitor memory
before large operations where possible. - Use chunked processing for
longer clips. - Warn before jobs that exceed configurable duration or
disk-space limits. - Do not promise real-time performance.

SECURITY AND PRIVACY - Default API host: 127.0.0.1. - No telemetry,
analytics, remote logging, automatic uploads, or remote model
inference. - Sanitize uploaded filenames and use generated job IDs. -
Restrict file access to approved job directories. - Do not allow
arbitrary paths or command arguments from the UI. - Use safe subprocess
argument lists rather than shell string concatenation. - Do not store
voice references longer than needed without explicit user choice. - Add
a clear delete-job-data function, with confirmation. - Keep user media,
logs containing personal paths, model weights, and generated outputs out
of Git. - Clearly explain that model downloads and software updates may
contact external sites when the user initiates them.

QUALITY - Keep source transcript, corrected transcript, translated text,
generated speech, and final timing linked by segment IDs. - Preserve the
reviewed translation; do not silently rewrite it during rendering. -
Report when timing adjustment changes speech speed or pauses. - Keep raw
and processed audio separate for comparison. - Provide audio preview
before final rendering. - Keep the original input immutable.

TESTS - Unit tests should not require downloaded models or a GPU. - Use
fake/mock model adapters for most CI tests. - Real model tests must be
opt-in and document the required model checkpoint. - Test malformed
input, missing audio, unsupported codec, empty transcript, translation
failure, TTS failure, cancellation, insufficient disk space, and export
failure. - Run formatters, linting, type checks, and tests supported by
the repository. - Do not report tests as passed unless the command
actually ran and returned success.

The completed product is a local AI dubbing studio, not merely a text

English video to Hindi-dubbed video, with editable translations, tested
